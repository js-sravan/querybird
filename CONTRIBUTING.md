## Getting Started

1. **Fork** the repository on GitHub
2. **Clone** your fork locally:
   ```bash
   git clone https://github.com/YOUR_USERNAME/querybird.git
   cd querybird
   ```
3. Add the upstream remote so you can stay up to date:
   ```bash
   git remote add upstream https://github.com/sravanjs/querybird.git
   ```

## Development Setup

### Prerequisites

| Tool | Version | Install |
|---|---|---|
| Go | 1.22+ | `brew install go` |
| Node.js | 20+ | `brew install node` |
| Wails CLI | v2 | `go install github.com/wailsapp/wails/v2/cmd/wails@latest` |
| Xcode CLT | latest | `xcode-select --install` |

Make sure `wails` is on your PATH:

```bash
export PATH="$PATH:$(go env GOPATH)/bin"
```

### Running in dev mode

```bash
wails dev
```

This starts the Go backend and the Vite hot-reload server together. Changes to `frontend/src/` appear instantly in the app window without restarting.

### Running tests

```bash
# All tests (no database required)
go test ./...

# PostgreSQL integration tests (requires a running PostgreSQL instance)
DBCLIENT_TEST_PASSWORD=yourpassword go test .
```

## Project Structure

```
querybird/
├── app.go                  # Backend methods exposed to the frontend via Wails
├── main.go                 # App entry point, window configuration
├── internal/
│   ├── models/             # Shared Go types (ConnectionConfig, etc.)
│   └── postgres/
│       ├── connection/     # Connect / disconnect / health check
│       ├── metadata/       # Schema introspection queries
│       └── query/          # SQL execution, editable result sets
├── frontend/
│   ├── src/
│   │   ├── App.tsx         # Entire UI — components, state, handlers
│   │   └── App.css         # All styles, design tokens, dark/light themes
│   ├── public/             # Static assets served at runtime
│   └── wailsjs/            # Auto-generated JS bindings (do not edit)
└── packaging/
    └── dmg/                # macOS DMG assets (icons, backgrounds)
```

### Key points

- **`app.go`** is the boundary between Go and the frontend. Any new backend capability needs a public method here with the correct Wails binding pattern.
- **`frontend/wailsjs/`** is auto-generated by `wails dev` / `wails build` — never edit these files manually.
- **`App.tsx`** is a single-file component. For larger additions, consider splitting into smaller files under `frontend/src/`.
- **Design tokens** live at the top of `App.css` as CSS custom properties. Use them instead of hardcoded colours.

## Making Changes

### Branching

Always create a feature branch off `main`:

```bash
git checkout main
git pull upstream main
git checkout -b feature/my-feature
# or
git checkout -b fix/bug-description
```

### Branch naming

| Type | Pattern | Example |
|---|---|---|
| Feature | `feature/<short-description>` | `feature/export-csv` |
| Bug fix | `fix/<short-description>` | `fix/reconnect-banner` |
| Docs | `docs/<short-description>` | `docs/update-readme` |
| Refactor | `refactor/<short-description>` | `refactor/split-app-tsx` |

### Commit messages

Use short, descriptive imperative sentences:

```
Add CSV export for query results
Fix reconnect banner not dismissing on success
Update README with DMG build instructions
```

## Code Style

### Go

- Follow standard Go formatting — run `gofmt` or `goimports` before committing
- Keep exported functions documented with a comment
- Errors should be wrapped with context: `fmt.Errorf("connect: %w", err)`
- No global state outside of `App` struct

### TypeScript / React

- Follow the existing patterns in `App.tsx` — functional components, `useState` / `useMemo` hooks
- CSS class names follow BEM-like conventions already in `App.css` — add new classes there
- Use the existing CSS custom properties (`var(--text-1)`, `var(--accent)`, etc.) — no hardcoded colours
- No new npm dependencies without discussion in an issue first

### General

- Minimal changes — only modify what is needed for the task
- No commented-out code
- No `console.log` left in production paths

## Submitting a Pull Request

1. Push your branch to your fork:
   ```bash
   git push origin feature/my-feature
   ```

2. Open a Pull Request against `main` on the upstream repo

3. Fill in the PR description:
   - **What** does this change do?
   - **Why** is it needed?
   - **How** was it tested?
   - Screenshots if it changes the UI

4. A maintainer will review and may request changes

5. Once approved, the PR will be merged — thanks!

## Reporting Bugs

Open an [Issue]([https://github.com/sravanjs/querybird/issues](https://github.com/js-sravan/querybird/issues)) and include:

- QueryBird version (from Help → About)
- macOS version
- Steps to reproduce
- What you expected vs what happened
- Any error messages from the app

---

## Requesting Features

Open an [Issue]([https://github.com/sravanjs/querybird/issues](https://github.com/js-sravan/querybird/issues)) with the label `enhancement` and describe:

- The use case — what problem does it solve?
- Proposed behaviour
- Any alternatives you considered
